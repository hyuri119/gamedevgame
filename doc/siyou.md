# ゲーム会社経営シミュレーション 新作 仕様書 (ドラフト)

> 本仕様書は既存ゲーム「ゲーム発展途上國2DX」(カイロソフト, 2001, VB6製)のバイナリ解析結果と、
> 公開攻略サイトから収集したデータを基に、新規開発するゲームのためのドラフトです。
> 大きなLLMでのブラッシュアップを前提に、事実ベースのデータと新規構想を明確に分けて記載しています。

## 0. ドキュメント概要

| 項目 | 内容 |
|---|---|
| タイトル | ゲーム会社経営シミュレーション（仮称） |
| 目的 | 「ゲーム発展途上國2DX」の面白さを土台に、よりゲーム会社経営らしい体験（新スタジオ発足・買収等）を追加した新作を作る |

## 1. コンセプト

### 1.1 ゲームの芯（既存作から受け継ぐ）
- **ゲーム会社を経営して、ゲームソフトを開発・発売し、資金を増やしていく**経営シミュレーション
- 時間軸は週単位で進行。リアルタイムに社員が動く
- 社員を雇用・育成し、開発チームを作る
- ハード（ゲーム機）のライセンス取得→ソフト開発→出荷→売上
- 売上本数、ランキング、コンテスト受賞、自社ハード開発など複数の「目標」を持つ
- 出荷しすぎると不良在庫、売れ残りで利益が圧迫されるシビアさ

### 1.2 新作で強化したい点（ユーザー要望）
1. **ゲーム会社経営らしい深いシステム**
   - 新スタジオ発足（分社化）
   - 会社買収（他社買収 / 自社買収回避）
   - グループ経営
2. **現代的なハードの登場**（データ駆動で自由に定義可能に）
   - 多メーカー混在の現行機種風ハード
3. **データ駆動設計**
   - ジャンル・内容・ハード・社員・イベントをJSONで定義 → 追加が簡単

### 1.3 対象外（削除・非実装）
- ミニゲーム（ポーカー、ブラックジャック、カードチェンジ、競馬、ナゾプンテ）

## 2. 基本プレイループ

```
┌────────────────────────────────────────────┐
│  1. 社員を雇用・育成                        │
│  2. ハードライセンスを取得                  │
│  3. ゲームソフトを開発（企画→開発→仕上げ） │
│  4. 出荷・販売                              │
│  5. 売上で資金獲得 → 拡張（繰り返し）       │
└────────────────────────────────────────────┘
```

- 週単位で進行。社員は各週に仕事をする
- 4月に社員の年俸支払い、年度末に翌年分の契約金支払い
- 資金不足で年俸払えないと銀行借金（返済期限1年・年利30%）
- 破産するとゲームオーバー

### 主要画面（既存作ベース）
- メインビュー（オフィス、社員、机、休憩室）
- ツールウィンドウ（社員一覧、テクノロジー、設定）
- 各種ダイアログ（開発、出荷、ライセンス、テナント、コンテスト等）

## 3. コアシステム詳細

### 3.1 社員
#### パラメータ
| パラメータ | 説明 |
|---|---|
| レベル | 上がると能力上昇。ただし年俸も上がる |
| おもしろさ | ゲームの面白さパラメータへの寄与 |
| 独創性 | ゲームの独創性への寄与。大ヒットに繋がることもある |
| グラフィック | グラフィック品質への寄与 |
| 音楽 | 音楽品質への寄与 |
| ひらめき度 | 開発時のイベント等 |
| 開発速度 | 開発の進行速度 |
| ストレス | 高くなると休憩室へ行く。0~100 |
| 年俸 / 契約金 | 雇用・維持コスト |

※ 既存作では「おもしろさ＆独創性 ＞＞ グラフィック＆音楽」が売上の優先度。

#### 役職（スマホ版++から流用可）
- プログラマ / シナリオライター / デザイナー / サウンドクリエイター / ディレクター / プロデューサー / ハードエンジニア / スーパーハッカー
- 進化条件（++の例）:
  - プログラマ Lv5 + シナリオライター Lv5 → ディレクター
  - デザイナー Lv5 + サウンドクリエイター Lv5 → プロデューサー
  - ディレクター Lv5 + プロデューサー Lv5（6役職Lv5） → ハードエンジニア
  - ハードエンジニア Lv5 → スーパーハッカー（最強職）
- スーパーハッカーは大規模オフィスでないと雇えない

#### 教育（++から流用候補）
- 教育方法を選んで能力育成（海外旅行・パチンコ等）
- 教育にはPOWER（行動力）と資金が必要
- 研究データを使った教育もある

#### 性格・名前
- 既存作には実在人物のもじりキャラ多数（攻略Wikiに一覧あり。§6参照）

#### 内容 × ジャンル組み合わせ（スマホ版++データを基にした参考表）
- ゲームの評価は「内容 × ジャンル」の相性で変動
- 相性マーク: ☆=傑作 / ◎=独創的 / ◯=まあ良い / ◇=なし / △=微妙 / ✕=悪い
- ジャンル20種 × 内容79種の**完全な組み合わせ早見表**を `data/data/kumiawase.csv` に保存済み（攻略Wiki ゲーム発展国++ 内容×ジャンル一覧表より抽出）
- 実装時はCSVをJSONに変換してデータとして読み込む
- 注: ジャンル「シミュレーションRPG・教育・カードゲーム」は全内容と相性コメントが発生しない（全て◇扱い）。内容「港湾・タイムスリップ・スパイ・芸能人」も同様

#### ストレス（実装）
> パラメータ表の「ストレス」行（0〜100）を実装済み。詳細は `src/lib/office.svelte.ts` の `updateStress()`。数値は仮置き。

- `Employee.stress`（0〜100）と `resting`（休養中フラグ）を持つ
- **週次更新**: 進行中プロジェクト（開発 / DLC / 受注 / 自社ハード / アーケード）が1つでもあれば `+2 × (1 - 上昇軽減率)` / 週、無ければ `- 休息時回復` / 週（休憩室 Lv で回復量・軽減率が変わる。§3.8 参照）
- **能力補正**: 実効能力値（`effStats`）は stress 50 超から逓減し、**最大15%低下**（stress 100 で -15%）
- **休養**: stress 100 到達で休養（`resting = true`）に入り、開発速度・能力平均から除外される（`activeEmployees()` が対象を返す）。休養中は `休息時回復 × 2` / 週で回復し、**30以下で復帰**（Lv1 なら約7週）
- 退職・ゲームオーバーにはつながらない（緩い設計）
- 休憩室はテナントではなくオフィス設備として実装（§3.8）

### 3.2 ゲーム開発
#### 開発タイプ
1. **オリジナルゲーム開発** - 自社の能力のみで勝負
2. **漫画・アニメをゲーム化** - 原作人気が売上に寄与（契約金が必要）。アニメ版のゲーム化も可
3. **続編を開発** - 殿堂入り作品のみ可能。前作パラメータ引き継ぎ

#### 開発工程（既存作）
1. 企画会議 → 開発案決定（バランス型 / おもしろさ重視 / 独創性重視 等）
2. 企画書完成 → 対象年齢・ジャンル選択
3. α版完成 → ゲーム内容決定
4. β版完成 → ジャンル選択
5. バグ取り → 完成 → 出荷

#### 開発期間とハード性能（作り込み）
- 開発に必要な工数（`devTarget`）は**対象ハードの性能（power）に比例**する（power×120）。高スペック機ほど作り込み（グラフィック・音楽等）の上限が高く、その分開発に時間がかかる
- グラフィック・音楽はハード性能の上限（power×10）でキャップされる（おもしろさ・独創性はキャップなし）
- 目安: 性能1（ファミオン）で約3か月、性能10（プレステータス5）で約4〜6か月
- **PCの性能は時代で変動**（`pcPower`）: 1983年=1、10年ごとに+2（1993=3、2003=5、2013=7、2023=9）。据え置きハードと違い、PCは年を追うごとにスペックが伸びて作り込みの上限も上がる

#### ゲームのパラメータ
- おもしろさ / 独創性 / グラフィック / 音楽 / バグ量 / 知名度
- バグが多いと回収命令（大損）

#### ジャンル × 内容（組み合わせ）
- 組み合わせ次第で評価が変わる（傑作 / 独創的 / まあ良い / 微妙 / 悪い）
- 既存作のジャンル: シミュレーションRPG、教育、カードゲーム等
- **教育・カードゲームは基本的に売れない。シミュレーションRPGはそこそこ売れるが爆売れしない**（++攻略情報）
- ジャンルと内容の組み合わせ一覧は攻略Wiki参照（wikiwiki.jp/kairoparknew/gamedev/08）

#### 開発方針（++から流用候補）
- 通常開発 / 速度重視 / 研究重視 / 予算増額
- 序盤は研究重視、後半は予算増額が効率的

#### 方向性ポイント（++から流用候補）
- ジャンルがレベル2・レベル5に上がる度に2ポイント獲得
- ジャンル・内容に合った方向性に割り振ると開発効率UP
- 方向性項目は最大8個まで

#### 販売の仕組み
- 出荷から6週間が「発売キャンペーン」で、この間が最も売れる（減衰カーブ）
- 発売初回の週が最も売れる
- 7月・12月（夏休み・冬休み）は販売数が上がりやすい
- キャンペーン終了後は**カタログ**に移行し、**ロングテール販売**（期待売上の約0.5%/週、累計は期待売上の1.5倍まで）が継続する
- 在庫が売り切れたら**再出荷**可能（カタログから、生産費を払って再入荷）
- たまに「話題」になると一時的な販売スパイク（再燃）が発生
- 売れ残りはリサイクルショップで処分（テナントがあれば買い取り）

### 3.3 ハード（ゲーム機）
#### 種類
- 家庭用ゲーム機 / 携帯型ゲーム機
- 媒体: カセット / CD 等

#### 仕組み
- ライセンス取得でそのハード向けに開発可能
- ライセンスは出荷台数が一番多い機種に絞るのが効率的（攻略情報）
- 古いハードは発売終了 → そのハードでは作れなくなる
- 自社ハード開発: ハードエンジニアが1人いれば可能

#### 自社ハード開発（既存作 + ++要素）
- 家庭用 / 携帯型の選択
- 高性能な部品を選ぶほど開発費が高い
- ++最強構成例: CPU「ポテトチップ」+ メディア「パンチカード」+ 据え置き型、開発費約1900億（1,900,000万）
- 自社ハード開発中はソフト開発ができず収益が一時的に減るが、完成後は爆増
- 自社ハードで続編を量産すればライセンス費用0円で稼げる

### 3.4 テナント（既存作）
会社経営の補助機能。同時に最大3つ選択。
| テナント | 効果 |
|---|---|
| ゲーム専門学校 | 毎年4月に優秀な卒業生を安価に雇用可能 |
| 社員温泉 | ストレスを0に。長く開発を続けられる |
| リサイクルショップ | 売れ残り在庫を買い取ってもらう |
| テクノロジー修行所 | 社員1人あたりのテクノロジー習得上限を増やす |
| カジノ | ※ミニゲーム廃止に伴い、設計要再検討（資金源として別機能化 or 削除） |
| 弁護士事務所 | 小売店・運送会社の手数料を引き下げ |
| ナゾプンテ研究所 | ※ミニゲーム廃止に伴い削除 or 別機能化 |
| 大型生産力開発所 | 一度に出荷できる本数（生産力）を大幅UP |
| 新ハード研究所 | 自社ハード開発を補助 |

※ ミニゲーム削除に伴い、カジノ・ナゾプンテは設計見直しが必要。
※ **社員温泉（ストレスを0に）はテナントではなく、オフィス設備の「休憩室」として実装した**（§3.8 参照。ストレスは0にするのではなく、休養で徐々に回復する方式）

### 3.5 テクノロジー
- 購入 → 社員に習得（必要経験値・習得時間あり）
- テクノロジーは「ゲーム開発の実力を底上げ」する（例: 要領圧縮）
- 代表的なもの: **要領圧縮**（開発コスト削減。攻略上最重要テクノロジー）
- テクノロジーをすべてOnにしないと完成しないハードもある

### 3.6 イベント
- 企画会議（開発案の決定・やり直し）
- 高度なプログラム挑戦（成功でポイント急増 / 失敗でバグ急増）
- 雑誌社からの取材（知名度UP）
- ゲームデックス出展（知名度大幅UP。開発中のソフトを出すのが効果的）
- 全日本ゲームコンテスト（グランプリ / 準グランプリ / デザイン賞 / 音楽賞 / クソゲー賞）
- クロスレビュー（雑誌レビュー。32点以上で殿堂入り）
- ネット対戦相手の発売ゲームチェック
- 引き抜き交渉（他社社員を引き抜く / 自社社員を引き抜かれる）

### 3.7 ランキング・実績
- 到達時間ランキング（100万本出荷、自社ハード発売等の目標達成までの年数）
- ソフト売上ランキング100
- 通算ランキング
- 殿堂入りゲーム数
- 会社ランク / ライブラリ度数 / ユーザー数

### 3.8 オフィス（++から流用候補）
- 小規模 → 中規模 → 大規模と移転で拡張
- 移転条件（++）:
  - 中規模: 4年目以降、資金1億円以上
  - 大規模: 4年目12月3週以降、資金3.5億円以上、かつ音楽賞・デザイン賞各1回以上受賞
- オフィスの着せ替え機能（+++）

#### オフィス（実装）
> 規模3段階・移転・家賃・社員上限・休憩室を実装済み（`data/offices.json`・`src/lib/office.svelte.ts`）。移転は**段階的（小→中→大）でダウングレード不可**。数値はすべて仮置き。

| 規模 | 社員上限 | 週次家賃 | 描画机数 | 移転費 | 移転条件 |
|---|---|---|---|---|---|
| 小規模 | 4人 | 10万円 | 4 | なし（初期） | — |
| 中規模 | 8人 | 80万円 | 6 | 1億円 | 4年目以降 |
| 大規模 | 14人 | 250万円 | 8（2段レイアウト） | 3.5億円 | 4年目12月以降 かつ 資金3.5億円以上 かつ デザイン賞・音楽賞の受賞が各1回以上 |

- **家賃**: 月の**第1週**に月額（週次家賃×4）を支払う（毎週ではない）。免除などの安全弁はなし
- **年俸**: 毎年4月に支払い。物価スライド（年+4%）込みの額を支払い、支払い後に各社員の年俸が定期昇給（+2%/年）する。数値は仮置き
- **社員上限**: 雇用は `maxEmployees()`（現オフィスの capacity）まで。スーパーハッカーは大規模オフィスでないと雇えない（§3.1）。買収（`acquireCompany`）で付いてくる社員も上限チェック対象（上限時は引き継がれない）

#### 休憩室（実装）
> テナント（§3.4）ではなく、**最初からオフィスにある設備**として実装。資金でアップグレード（Lv1〜5）。

| Lv | 改修費 | 休息時回復（/週） | ストレス上昇軽減 |
|---|---|---|---|
| 1 | なし | 5 | 0% |
| 2 | 2,000万円 | 7 | 10% |
| 3 | 5,000万円 | 9 | 20% |
| 4 | 1億円 | 11 | 30% |
| 5 | 2億円 | 13 | 40% |

- ストレスロジックとの連動は §3.1「#### ストレス（実装）」参照

#### 机・レイアウト（実装）
> オフィスの内装設計。机の増設とレイアウト方針の選択で開発効率が変わる。数値はすべて仮置き。

- **机**: 初期机数は小4/中6/大8。資金（1机500万円）で社員上限と同数まで増設できる。移転すると新オフィスの既定値に戻る。オフィス画面の描画机数にも連動する
- **混雑度**（社員数÷机数）: 1未満＝快適（開発速度×1.05）、1〜1.5＝普通（×1.0）、1.5超＝混雑（×0.9・開発中のストレス+1/週）
- **レイアウト方針**（`game.layout`、いつでも変更可）: 集中型（速度×1.1、ストレス+0.5/週）/ 標準（補正なし）/ ゆったり型（開発中のストレス上昇×0.7）
- 速度補正は週進行の開発・DLC・受注・アーケードの進行速度に一律適用（`layoutSpeedMul()`）

### 3.9 周回（++から流用候補）
- 21年目1月を越えたら「最初から」で2周目可能
- 引き継ぐもの: ジャンル・内容のノウハウレベル、方向性ポイント

### 3.10 競合ソフト（販売されるソフト）年表
> 市場に出回る他社タイトルを史実ベースで時系列化。詳細は `data/software.json`（1983〜2025、各年3〜5本、137本収録）。

- 各タイトルは `genre`（ジャンル20種）と `content`（内容79種）を **data/kumiawase.csv と完全一致する文字列** で保持 → 相性評価（§3.1）と直接連動できる
- `sales` は国内概算出荷本数。バランス校正の目標値として使う
- タイトル・企業名は史実の参照名（任天堂等）。ゲーム内ではパロディ名に置換予定（ハード同様）
- 用途: プレイヤー作品と競合する市場モデル、売上ランキング、発売日被り（§4.4）、ライバル企業の引き抜き対象（§3.6）の対抗要素
- 代表例: 1985 スーパーマリオブラザーズ(681万本) / 1996 ポケモン赤緑(822万本) / 2006 Wii Sports(370万本) / 2020 あつまれ どうぶつの森(1000万本)

## 4. 新規追加要素（ユーザー要望の強化点）

### 4.1 新スタジオ発足（分社化）
- 一定規模（資金・社員数・売上）に達すると「新スタジオを発足」できる
- スタジオごとに:
  - 独立した開発ライン（複数タイトルを並行開発可能）
  - スタジオ名・担当ジャンル・ターゲット層を設定
  - 独立した予算・売上・評価
- グループ全体の管理画面（連結決算、売上比率）
- スタジオ発足には資金と、責任者となる優秀な社員が必要

### 4.2 会社買収
#### 他社の買収
- 買収候補の会社（規模・保有ジャンル・社員・ハードライセンス）を調査
- 買収額交渉（相手の業績・規模で変動）
- 買収後:
  - 相手の社員・ジャンル・内容・テクノロジー・ハードライセンスを獲得
  - 買収した会社は子会社として運営 or 統合を選択
  - 子会社は独自の開発ラインとして活用
#### 買収のリスク
- 買収に失敗すると交渉費用を失う
- 過大な買収で資金ショート（破産リスク）
- 買収企業の負債や質の悪い社員も引き継ぐ
#### 自社が買収される危機
- 資金・評価が低いと他社に買収されそうになるイベント
- 防衛策: 資金確保、友好的買収提案、買収防衛（ポイズンピル的要素）など

### 4.3 グループ経営
- 持ち株会社として複数スタジオ・子会社を統括
- グループ内での人材異動、技術共有
- グループ売上・グループランキング

### 4.4 その他の経営強化案
- **クリエイター契約**: 外部の著名クリエイターをタイトル単位で起用
- **独占タイトル**: 特定ハード専用タイトルの開発（手数料優遇等）
- **発売日戦略**: 他社の人気タイトルと発売日が被ると売上が分散
- **マーケティング投資**: 広告・TV番組紹介（出荷本数に影響、早いほど効果大）
- **オフィス設計**（実装）: 机の増設とレイアウト方針（集中型/標準/ゆったり型）で開発効率が変わる（§3.8「#### 机・レイアウト」参照）
- **ファンコミュニティ**: ファン数が増えるとブーム・行列が発生
- **自社ハードのライセンス収入・ネットワーク維持**（アイデア）: 自社ハードを持てば、他社ソフトへのライセンス料徴収や、ネットワークサービス（オンライン機能）の維持費と収益を扱える
- **パブリッシャー業務**（アイデア）: 外部開発スタジオのソフトの発売・販売を請け負う
- **職業の追加**（アイデア）: 現状8職種（プログラマ/シナリオ/デザイナー/サウンド/ディレクター/プロデューサー/ハードエンジニア/スーパーハッカー）から増やす
- **受注開発（外注納品）**（アイデア・スマホ版++要素）: 序盤の資金源として、他社から開発案件を受注して納品する
- **オファー**（アイデア）: 知名度が上がるとアニメ・漫画のゲーム化オファーや独占タイトル依頼が届く
- **独占ライセンス交渉**（アイデア）: 他社から独占契約込みでライセンスを借りる交渉（他社と差別化）
- **DL販売**（アイデア）: 時代が進むと出荷（パッケージ）とは別に、ダウンロード販売チャネルで継続的に売れる要素（PCストア等と連動）
- **アップデート・DLC**（アイデア）: 発売済み作品にアップデートやDLC（追加コンテンツ）を配信して継続売上・知名度を得る要素。DLストア（§4.4）や運営型（§4.6）と親和性が高い

#### アップデート・DLC（実装）
> カタログ作品（発売済み）に対してDLCを制作・配信する。DLストア経由のデジタル販売で、在庫管理が不要な点がパッケージ出荷と異なる。

- **解放条件**: DL対応ハード（PC または media に「ダウンロード」を含む）のカタログ作品＋DLストア解禁年以降
- **開発工程**: スタジオ1つを占有（本編開発・受注とは枠を共有）。バグ取り工程はなしの単純進行。開発目標値 = ハードpower×30（本編 power×120 の 1/4）。制作費 = power×10万円
- **複数出し**: 本数上限なし。n本目の売上期待値 = `expectedSales × 10% × 0.6^(n-1)` で逓減。価格は本体の 1/4 固定
- **評価**: 完成時にレビュー点を算出（本編スコア 70% ＋ チームのおもしろさ/独創性 ＋ 乱数。40点満点スケール）
  - DLC自体の売上係数 = `0.7 + (レビュー/40) × 0.6`（0.7〜1.3倍）
  - 高評価（32点以上）で知名度 +2
  - **本編再燃**: 評価が良いほど本編のロングテール需要上限を引き上げ（最大 +30%）し、発売後8週間は本編の週次需要もブースト。ブースト中は在庫切れ分もDL販売（売上単価7割）で消化
- **販売**: 完成〜6週間、`SALES_SHARE` を流用した週次売上。手数料 = ストアcommission（30%）。生産費なし
- 数値は仮置き。§10 の校正時に調整すること

### 4.5 アーケードゲーム参入（業務用ゲーム）
> 家庭用ソフトとは別の収益モデル（インカム）を持つ新たな開発ライン。史実データは `data/hardware.json` の type=arcade 基板（10種）と `data/software.json` の arcadeGames（15本）。

#### 概要
- 業務用基板（アーケード）向けにゲームを開発し、ゲームセンター等へ展開する
- 出荷本数ではなく「ロケテスト → 稼働率 → インカム（コイン収益）」で収益化
- 稼働率は「おもしろさ・独創性」と、対戦・体感・音楽ゲーム等の業務用向き要素で決まる

#### 仕組み（案）
1. **基板の選択**: 他社基板を借りる（ライセンス料）か、自社基板を開発（開発費が高いがロイヤリティ0）
2. **開発**: 家庭用と同様の工程（§3.2）。業務用ならではの「対戦」「体感」「大型筐体」を盛り込みやすい
3. **ロケテスト**: 数週間の試験稼働で反応を見て、本稼働/修正を判断（§3.6 のイベント候補）
4. **稼働・インカム**: 稼働率に応じたコイン収益が週単位で入る。人気が続く限り長期収益

#### 家庭用とのシナジー（移植）
- 高稼働のアーケード作品は「知名度」が付いた状態で家庭用へ移植でき、ヒットしやすい（史実: ストII→SFC 290万本、バーチャファイター2→サターン 130万本）
- 逆に家庭用ヒット作のアーケード展開も可能
- 移植時は既存の「内容×ジャンル」評価（data/kumiawase.csv）を再利用

#### データ
- 基板: `data/hardware.json`（ナムコ基板・セタガヤ システム16・CPS・ネオンジオンMVS・セタガヤ モデル2・NAOMI・タイトー タイプX 等10種）
- 代表作: `data/software.json` の arcadeGames（スペースインベーダー・パックマン・ストII・DDR・太鼓の達人 等15本）

### 4.6 運営型ゲーム（ライブサービス）※将来的な構想
> 買い切り（出荷本数）型に加え、継続収益を得る「運営型」を追加する構想。**スマホ（プラットフォーム）と運営型（ビジネスモデル）は直交する**ため、どちらか一方に絞らず統一的に設計する。

#### 2つの軸
- **プラットフォーム軸**: スマホ（iOS/Android）を新規ハード種別として追加（普及台数は家庭用機より桁違いに大きい）
- **ビジネスモデル軸**: 買い切り（出荷本数・§3.2）に加え、運営型（継続収益）を追加

#### 運営型の2形態
1. **MMO（月額課金）**: PC/コンソール。`ネットRPG`/`ネットSLG` ジャンル（既存）で分類。史実: FF11・FF14・ドラゴンクエストX・リネージュ
2. **ソシャゲ（F2P＋ガチャ）**: スマホ。スタミナ・ログインボーナス・期間イベントで運用。史実: パズドラ(2012)・モンスト(2013)・FGO(2015)・ウマ娘(2021)

#### 収益モデル（案）
- 指標: **MAU（月間アクティブ）× ARPU（ユーザー単価）− 運営コスト**
- 開発後も「運営」フェーズが続く（アップデート・イベント・ガチャ更新・バランス調整）
- 週単位進行（§2）と相性が良い: 週ごとに課金収益・MAUが変動し、運営イベントで維持する
- 買い切り型との対比: 初動の出荷が全て vs 長期課金（ヒットすれば桁違い、失敗すれば運営コストが赤字に）

#### データ拡張（実装時に）
- スマホを `data/hardware.json` に新規ハード種別（type=mobile）として追加
- MMO/ソシャゲの代表作を `data/software.json` に追加（ネットRPG/ネットSLG ジャンルで分類）

### 6.1 ゲーム発展途上國2DX 攻略メモ（既存作の効率的プレイ）
- **開始時**: 契約金2000万程度のレベル4〜6社員を4人雇う。初期レベル1キャラは解雇
- **秘書設定**: 「3億以上で生産UP」「ストレス80になったら休憩」「ストレス20になったら戻す」
- **テクノロジー**: 「要領圧縮」を最優先で購入・習得（レベル2推奨）
- **開発案**: バランス型 or おもしろさ・独創性型が出るまで会議をやり直す
- **ジャンル**: 開発量が高く費用が安い物を選ぶ
- **宣伝**: 開発中の新聞広告等は不要（+では必要）
- **デックス出展**: 開発中のソフトのみ出す
- **ライセンス**: 出荷台数が一番多い機種1つに絞る
- **資金6億**: 64ブルーPCに買い換え
- **資金8億**: 専門学校建設
- **殿堂入り後**: すぐ続編開発
- **在庫20万以上**: リサイクルショップ活用
- **生産力**: 大型生産力開発所でとにかく上げる（手動が効果的）
- **1回の出荷**: 中盤で7〜80万本、終盤で100万本単位
- **出荷テク**: 週変わり直前の秘書お知らせタイミングで即座に再出荷（発売直後は在庫が一瞬でなくなる）
- **グランプリ**: おもしろさ・独創性・グラフィック・音楽の4パラメータ全て150以上（++の条件）
- **総売上例**: 2500億円 / 860万本ビッグタイトル / グランプリ数十回（攻略者実績）

- **アイテム屋**（5月に「転職の教科書」を購入等）

## 7. 技術スタック（確定）

> 未経験者でも扱いやすい最小構成。UI が大半を占める管理シムなので、メニュー・ダイアログ・表は **DOM（Svelte）**、社員が動くオフィス画面だけ **Canvas 2D** で描画するハイブリッド。

### 7.1 採用構成
| 項目 | 内容 |
|---|---|
| 実行環境 | ブラウザ（PC / スマホ） |
| ビルドツール | Vite（dev サーバ + HMR、設定ほぼゼロ） |
| 言語 | TypeScript |
| UI | Svelte（最も学習コストが低いリアクティブUI） |
| 描画 | オフィス画面のみ Canvas 2D（2Dドット絵風） |
| データ | JSON（`data/*.json` を直接 import。追加・調整が容易） |
| 状態管理 | ゲーム状態は Svelte ストア、セーブは localStorage / IndexedDB |

### 7.2 学習の進め方（未経験者向け）
1. 公式チュートリアル: Svelte 公式 (svelte.dev/tutorial) を一通り（数時間）
2. 雛形作成: `npm create vite@latest` → Svelte + TypeScript を選択
3. 以降は既存画面を真似て拡張。ゲーム特有の複雑ロジックは 100% TypeScript で書ける

### 7.3 採用しなかった候補
- Godot Engine — 動く画面は楽だが UI 大量の管理シムには Control ノードがやや弱く、Web 出力も重め
- Python + pygame — UI が手作りになり配布（ブラウザ/スマホ）とも噛み合わない
- Unity — 本格的だがこの規模では重い

### 7.4 素材
- 既存ゲームの `Graphic/*.bmp`, `Sound/*.wav` を流用可能（個人利用の範囲）
- 著作権は元ゲーム作者（カイロソフト）に帰属。商用化する場合は要注意

## 10. バランス設計（ドラフト）

> 史実データ（`data/hardware.json`・`data/software.json`・`data/kumiawase.csv`）を踏まえた売上連動の骨子。数値はすべて仮置きで、§10.6 の校正で確定させる。

### 10.1 売上期待値モデル
```
期待売上本数 = ハード普及台数(installBase) × 到達率
到達率 = 基本到達率 0.08 × 品質係数 × 相性係数 × 知名度係数 × 季節係数 × 市場成長係数
```
- 到達率は「そのハードの所有者のうち何割が買うか」の浸透率
- ハードの普及台数（installBase）が市場規模の上限。参入時期で選択肢が変わる
- **市場成長係数**（`marketGrowth`）: 1983年は 0.1（10%）からスタートし、毎年+0.05ずつ成長して最大1.0（2001年頃に飽和）。序盤は売上が1/10程度で、時代が進むごとに市場が拡大する

### 10.2 品質係数（0.5〜1.5）
- 主体は **おもしろさ・独創性**（§3.1: おもしろさ＆独創性 ＞＞ グラフィック＆音楽）
- グラフィック・音楽は補助。かつ **ハードの power を上限** とする（高性能ハードほど高品質を作れる）
- バグ量が一定を超えると回収命令（大損）で、売上はゼロに

### 10.3 相性係数（内容×ジャンル）
| マーク | 係数(仮) |
|---|---|
| ☆ 傑作 | 1.5 |
| ◎ 独創的 | 1.2 |
| ◯ まあ良い | 1.0 |
| ◇ なし | 0.85 |
| △ 微妙 | 0.7 |
| ✕ 悪い | 0.5 |

### 10.4 知名度係数・季節係数
- 知名度係数: 基礎 1.0 ＋ デックス出展・取材・TV紹介（§3.6）で最大 ~1.5
- 季節係数: 7月・12月 = 1.2〜1.3、通常 = 1.0（§3.2）

### 10.5 販売減衰カーブ
- 発売初週が最大（期待売上の 30〜40%）、以降 6週で減衰しほぼ終了
- 出荷数 > 実売 → 不良在庫（リサイクルショップで処分、週1回再出荷）

### 10.6 史実データでの校正
到達率の実績目安（`data/software.json` の sales ÷ installBase）:
- 超ヒット ~30〜40%: マリオ(35%)・ポケモン赤緑(39%)・あつ森(31%)
- 大ヒット ~20〜30%: FF7(21%)・Wii Sports(29%)・モンハンP3rd(24%)
- ヒット ~10〜20%: ドラクエIII(20%)・ストII(17%)・ドラクエIX(13%)

最良ケース = 0.08 × 1.5(品質) × 1.5(☆) × 1.5(知名度) × 1.3(季節) ≈ **0.35** で超ヒット帯に一致。平均的なソフト（各係数 1.0）は 0.08（8%）に落ち着く。係数はこの帯に合うよう最終調整する。
